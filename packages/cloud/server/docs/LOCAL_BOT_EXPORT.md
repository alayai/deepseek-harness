# Local Bot public export

The cloud plugin now has a separate Host-only `dshCloud/exportLocal` operation. It is deliberately not part of `readLocal`: the read-only provider returns bounded previews, while export asks a dedicated provider for a complete declarative definition. The Client uses this operation for a preview first and only posts after a second confirmation.

The operation requires the current cloud epoch and the Host owner. DS Bot returns a definition only when the roster is loaded and the Bot is public. Private, missing, uninitialized, invalid, or oversized Bots are refused before any dsh-server request. The exported definition contains only `schemaVersion`, name, role, instructions and an empty required-capability list. Local model references, credentials, folders, skills, connectors, memory, history, avatars and sessions stay local. The user must click the export action after choosing a Workspace; no export starts automatically. A retry after an unknown response reuses the saved idempotency key only after the current definition and scope still match.

The cloud panel checks `server-info.capabilities.workspaceBots`, shows the full name/role/instructions preview, and waits for a second explicit confirmation before posting the definition to `POST .../workspaces/:workspaceId/bots`. The request includes a `local-export` source with the local Bot ID, export version and timestamp. The server creates a new workspace Bot with the existing idempotency and RLS rules, records a SHA-256 content summary on revision 1, and exposes the source when that revision is read. Later local edits are published as explicit immutable cloud revisions; cloud revisions never rewrite the local Bot.

The client keeps a bounded `localStorage` index under `dsh.cloud.bot-sync.v1`. Each entry contains only the normalized server origin and server ID, the authenticated user, tenant and Workspace, local Bot ID, cloud Bot ID, revision/version, SHA-256 digest and synchronization time. It never stores the definition, credentials, files, memory, history, bearer token or a Bot prompt. The server ID and authenticated user are part of the key so a reused URL or a different account cannot reuse an old mapping.

When the local Bot list is opened again, the Host re-exports each public Bot for hashing and compares it with the stored mapping and the current immutable server revision. The panel reports synchronized, local update, cloud update, archived, unknown or pending export state. Publishing a local update always uses `expectedVersion` and appends an immutable revision. A pending request retains its original idempotency key; retrying a changed definition is refused until the original result is reconciled. A failed request is removed from the retry index only for a definitive server rejection.

The current increment does not provide bidirectional definition merge, private-Bot override, local skill migration, model credential migration, or main-chat projection. Full export remains subject to the server Bot definition limits and compatibility report.
